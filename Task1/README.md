# Задание 1. Исследование моделей и инфраструктуры

## 1. Сравнение LLM-моделей

| Критерий                 | Локальные (Hugging Face: Llama 3, Mistral, Qwen)                | Облачные OpenAI (GPT-4o)        | Облачные YandexGPT 5.1 Pro                                                              |
|--------------------------|-----------------------------------------------------------------|---------------------------------|-----------------------------------------------------------------------------------------|
| Качество ответов         | Хорошее, сопоставимо с облачными в RAG-сценариях                | Эталонное, высокое              | Высокое; по некоторым метрикам превосходит OpenAI GPT-4.1                               |
| Скорость                 | Зависит от железа; на GPU – быстро                              | Низкая задержка (API)           | Низкая задержка (API)                                                                   |
| Стоимость владения       | Нулевые OPEX после развёртывания; высокий CAPEX на GPU          | $0.03–0.12 за 1K токенов (OPEX) | OPEX, сопоставим с OpenAI                                                               |
| Простота развёртывания   | Сложнее; требует настройки инфраструктуры и управления моделями | Просто (API-ключ)               | Просто (API-ключ)                                                                       |
| Конфиденциальность       | Данные остаются внутри периметра                                | Данные уходят в облако OpenAI   | Данные уходят в Яндекс (дополнительные юридические риски для финско-эстонской компании) |
| Кастомизация             | Полная (дообучение, смена параметров)                           | Ограниченная                    | Ограниченная                                                                            |

Вывод: Для QuantumForge, с учётом строгих требований к конфиденциальности, локальные LLM предпочтительнее. Облачные решения могут использоваться только для нечувствительных данных (например, публичных FAQ), но основной поток запросов к коду и архитектуре должен обрабатываться локально.

## 2. Сравнение моделей эмбеддингов

| Критерий            | Локальные Sentence-Transformers (all-MiniLM-L6-v2)                                                     | Облачные OpenAI Embeddings (text-embedding-3-small) |
|---------------------|--------------------------------------------------------------------------------------------------------|-----------------------------------------------------|
| Размерность         | 384                                                                                                    | 1536                                                |
| Качество поиска     | Хорошее для большинства задач; некоторые модели (Stella) дают «отличную производительность из коробки» | Очень высокое, лучшее семантическое понимание       |
| Скорость индексации | Зависит от CPU/GPU; на CPU медленнее                                                                   | Быстро (API)                                        |
| Стоимость           | Бесплатно после развёртывания                                                                          | $0.02 за 1M токенов                                 |
| Конфиденциальность  | Данные локально                                                                                        | Данные уходят в OpenAI                              |
| Поддержка           | Активное сообщество, множество моделей                                                                 | Полная документация                                 |

Вывод: Для 21 000+ документов и требований к безопасности локальные эмбеддинги (all-MiniLM-L6-v2) — оптимальный выбор. Они обеспечивают достаточное качество при нулевой стоимости и полном контроле над данными. При необходимости можно использовать более мощные модели (например, `intfloat/e5-large-v2`) за счёт увеличения вычислительных ресурсов.

## 3. Сравнение векторных баз данных: ChromaDB vs FAISS

| Критерий                 | ChromaDB                                                                           | FAISS                                                                    |
|--------------------------|------------------------------------------------------------------------------------|--------------------------------------------------------------------------|
| Скорость поиска          | ~15–16.5 мс на запрос (QPS ~423)                                                   | ~5–20.7 мс (QPS ~652)                                                    |
| Скорость индексации      | Хорошая; масштабируется эффективнее FAISS при большом количестве документов на CPU | Быстрая, но требует больше памяти                                        |
| Сложность внедрения      | Простота; purpose-built векторная БД с метаданными                                 | Легковесная библиотека, требует больше кода для production-использования |
| Удобство работы          | Высокое: встроенное управление метаданными, фильтрация, persistence                | Низкое: только поиск, нет встроенного управления данными                 |
| Память                   | ~4.2 ГБ                                                                            | ~5.8 ГБ                                                                  |
| Масштабируемость         | До 200K векторов – отлично; свыше – FAISS эффективнее                              | До 10M+ векторов                                                         |
| Стоимость инфраструктуры | Низкая (лёгкая БД)                                                                 | Низкая (библиотека)                                                      |

Вывод: При текущем объёме (~21 000 документов → ~200 000 чанков) ChromaDB является наилучшим выбором благодаря:
- Достаточной скорости (~16 мс на запрос)
- Встроенной работе с метаданными (фильтрация по ролям, проектам, типам документов)
- Простоте внедрения и поддержки
- Меньшему потреблению памяти по сравнению с FAISS

FAISS может быть рассмотрен при росте базы до 1M+ векторов, когда потребуется более высокая производительность и готовность к сложной настройке индексов.

## 4. Рекомендуемая конфигурация сервера

| Компонент | Минимальная                   | Рекомендуемая           | Production             |
|-----------|-------------------------------|-------------------------|------------------------|
| CPU       | 8 ядер (Intel i7/AMD Ryzen 7) | 16+ ядер                | 32 ядра                |
| RAM       | 32 ГБ                         | 64 ГБ                   | 128 ГБ                 |
| GPU       | NVIDIA RTX 3090 (24 ГБ VRAM)  | NVIDIA RTX 4090 (24 ГБ) | NVIDIA A100 (40–80 ГБ) |
| Storage   | 500 ГБ NVMe SSD               | 1 ТБ NVMe SSD           | 2 ТБ NVMe SSD RAID1    |

Обоснование:  
- 8-ядерный CPU + 32 ГБ RAM достаточно для индексации и поиска в ChromaDB.  
- GPU (RTX 4090) необходим для быстрого инференса LLM (7B–13B параметров) в 4-bit квантовании.  
- 24 ГБ VRAM позволяет запускать модели до 13B параметров, что обеспечивает хорошее качество ответов.


## Итоговые варианты архитектуры

### Вариант 1: Полностью локальное решение (Рекомендуемый)

| Компонент    | Выбор                                                     |
|--------------|-----------------------------------------------------------|
| LLM          | Mistral 7B / Llama 3 8B (локально, через Ollama или vLLM) |
| Эмбеддинги   | all-MiniLM-L6-v2 (Sentence-Transformers)                  |
| Векторная БД | ChromaDB                                                  |
| Сервер       | 16 ядер CPU, 64 ГБ RAM, 1 ТБ NVMe SSD, RTX 4090           |

Преимущества:  
- Полная конфиденциальность данных  
- Нулевые операционные расходы (OPEX)  
- Полный контроль над моделью и инфраструктурой  

Недостатки:  
- Высокие первоначальные CAPEX (~$5,000–$8,000 за сервер)  
- Требуется DevOps-экспертиза для развёртывания  

### Вариант 2: Гибридное решение (облачная LLM + локальные эмбеддинги)

| Компонент    | Выбор                                     |
|--------------|-------------------------------------------|
| LLM          | OpenAI GPT-4o или YandexGPT 5.1 Pro (API) |
| Эмбеддинги   | all-MiniLM-L6-v2 (локально)               |
| Векторная БД | ChromaDB                                  |
| Сервер       | 8 ядер CPU, 32 ГБ RAM (без GPU)           |

Преимущества:  
- Высокое качество ответов (эталонные LLM)  
- Низкие CAPEX (не нужен мощный GPU)  
- Быстрый старт  

Недостатки:  
- Данные уходят в облако (риски для конфиденциального кода и архитектуры)  
- Постоянные OPEX (API-расходы)  
- Зависимость от внешнего провайдера  

### Вариант 3: Полностью облачное решение

| Компонент    | Выбор                         |
|--------------|-------------------------------|

## Выбор лучшего варианта

Рекомендуемый вариант: Вариант 1 – полностью локальное решение

Аргументация:
1. Конфиденциальность – критический фактор. QuantumForge работает с кодом микросервисов, архитектурными решениями и данными клиентов (ABB, Wärtsilä). Вынос этих данных в облачные API создаёт неприемлемые риски, особенно в контексте предстоящего аудита SOC 2.
2. Экономическая эффективность. При объёме ~21 000 документов и приросте ~400 страниц в месяц API-расходы на OpenAI составят:
   - Эмбеддинги: ~$0.02 × (21K документов × 5 чанков) = ~$2,100 в месяц только на индексацию новых данных  
   - LLM: ~$0.03–0.12 за 1K токенов × ~10M токенов/месяц = ~$300–1,200/месяц  
   - Итого: ~$2,400–3,300/месяц OPEX → окупает сервер за 2–3 месяца.
3. Качество локальных моделей. Согласно исследованиям 2025 года, локальные модели в RAG-сценариях показывают результаты, сопоставимые с облачными, а в некоторых случаях – даже лучше при правильной настройке.
4. Масштабируемость. ChromaDB на текущий объём (~200K векторов) работает эффективно. При росте до 1M+ векторов можно бесшовно мигрировать на FAISS или Milvus.
5. Соответствие аудитам. Локальное развёртывание упрощает прохождение SOC 2, так как все данные остаются под контролем компании, а доступ к ним можно детально логировать.

## Итоговый стек технологий

| Слой         | Технология                                                   | Обоснование                                                                               |
|--------------|--------------------------------------------------------------|-------------------------------------------------------------------------------------------|
| LLM          | Mistral 7B / Llama 3 8B (локально, через Ollama или vLLM)    | Баланс качества и требований к железу; open-source; конфиденциальность                    |
| Эмбеддинги   | all-MiniLM-L6-v2 (Sentence-Transformers)                     | Лёгкий (384 dim), быстрый, бесплатный, достаточное качество                               |
| Векторная БД | ChromaDB                                                     | Простота внедрения, работа с метаданными, эффективность на CPU, низкое потребление памяти |
| Сервер       | 16 ядер CPU, 64 ГБ RAM, 1 ТБ NVMe SSD, NVIDIA RTX 4090 24 ГБ | Обеспечивает быстрый инференс LLM и индексацию                                            |
| Оркестрация  | Docker + Kubernetes (существующий EKS)                       | Интеграция с текущим стеком AWS                                                           |
| Мониторинг   | Prometheus + Grafana                                         | Отслеживание качества ответов, нагрузки и задержек                                        |

Почему ChromaDB?  
ChromaDB выбран как векторная БД, потому что:
- Обеспечивает достаточную скорость (~16 мс на запрос) для текущего объёма  
- Проста в развёртывании и поддержке (не требует отдельной инфраструктуры)  
- Встроенная работа с метаданными позволяет фильтровать по ролям (разработчик/саппорт/менеджер) и типам документов  
- Меньшее потребление памяти по сравнению с FAISS  
- При росте базы до 1M+ векторов может быть легко заменена на FAISS или Milvus без изменения логики приложения
